# 18. 缺少数据库迁移机制

> **严重度**：🟡 关注
> **涉及文件**：`server/storage/database.js`
> **类型**：存储
> **状态**：✅ 已解决

## 问题描述

数据库 Schema 变更使用 `try/catch + ALTER TABLE` 的"伪迁移"方式：

```js
// database.js:56
try { db.run("ALTER TABLE feedback ADD COLUMN answer_content TEXT DEFAULT ''") } catch {}
```

### 问题

1. **假设变更幂等**：`ALTER TABLE` 成功时无事，失败时静默忽略。但如果 `answer_content` 列已存在但类型不同，不会被检测到
2. **无法回滚**：没有版本管理，无法回退到旧 Schema
3. **复杂迁移不可能**：列改名、数据迁移、表合并等复杂操作无法用这种方式实现
4. **生产环境风险**：直接在生产数据库上 `ALTER TABLE`，无测试验证

## 改进方向

1. 引入版本化迁移机制（如 Drizzle Kit、Knex 迁移）
2. 维护迁移文件表 `_migrations`，记录已执行的迁移
3. 每次启动时自动执行未应用的迁移
