# 08. 双前端维护成本高

> **严重度**：🟠 中等
> **涉及文件**：`public/index.html`（604 行）、`client/` 整个目录
> **类型**：架构

## 问题描述

项目维护两个功能重叠的前端：

| 对比 | React SPA (client/) | Vanilla JS (public/index.html) |
|------|:---:|:---:|
| 代码行数 | ~3000+ | 604 |
| 框架 | React 19 + TypeScript | 纯 HTML/CSS/JS |
| 构建 | Vite 6 | 零构建 |
| Dashboard | ✅ | ❌ |
| 权限弹窗 | ✅ | ❌ |
| 子会话导航 | ✅ | ❌ |
| Agent 选择 | ✅ | ❌ |
| 满意度反馈 | ✅ | ❌ |
| 暗色主题 | ✅ | ✅ |
| 在线地址 | `/` | `/`（兜底） |

### 问题

1. **双倍维护量**：修改 API 或消息结构时，两个前端都要改
2. **Vanilla JS 严重落后**：604 行代码无法复现 React 前端的丰富功能
3. **兜底策略不合理**：构建失败时提供功能残缺的界面，用户体验差

## 改进方向

1. 确保 React 构建永远可用（CI 中构建失败视为流水线失败）
2. 用服务端渲染（EJS/Handlebars）替代 Vanilla JS，由后端直接渲染关键 HTML
3. 或在 Vite 构建失败时提供友好的错误页面而非简陋的 Vanilla 版本
