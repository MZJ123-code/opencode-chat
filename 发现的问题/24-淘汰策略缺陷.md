# 24. evictOldestSession 淘汰策略有缺陷

> **严重度**：🟡 关注
> **涉及文件**：`server/services/sessionService.js:15-23`
> **类型**：后端
> **状态**：✅ 已解决

## 问题描述

当会话数量超过限制时，淘汰最旧会话的逻辑有缺陷：

```js
function evictOldestSession(ip) {
  const ids = ipSessions.get(ip)
  if (!ids || ids.size === 0) return
  const oldestId = ids.values().next().value  // 取 Set 的"第一个"
  ids.delete(oldestId)
  ipUsers.get(ip)?.sessionIds.delete(oldestId)
  sessionMeta.delete(oldestId)
}
```

### 问题

1. **Set 的"第一个"不等于最旧的**：`ipSessions` 是数组（有序），但 `evictOldestSession` 实际从 `ids`（Set）取第一个元素，Set 的迭代顺序是插入顺序，但这里 `ids` 实际上是 `ipSessions.get(ip)` 返回的数组？不，看代码：`const ids = ipSessions.get(ip)`，`ipSessions` 是 `Map<string, string[]>`，所以 `ids` 是数组。数组有 `.values()` 但它的 `.next().value` 是第一个元素（最早插入的）... 但 JS 数组的 `.values()` 返回的是迭代器，确实是第一个元素。

   Wait, 让我重新审视：`ipSessions` 是 `Map<string, string[]>`。`ipSessions.get(ip)` 返回一个数组。`ids.values()` 返回数组的迭代器。`ids.values().next().value` 返回数组第一个元素。

   但问题是：**数组可能会因为其他操作（如 SSE 事件流中的 push）而改变顺序**，并不保证始终按创建时间排序。

2. **全局淘汰扫描整个 Map**：当全局超过 5000 会话时，遍历整个 `sessionMeta` 找到最旧的：

```js
for (const [id, meta] of sessionMeta) {
  if (meta.createdAt < oldestTime) {
    oldestTime = meta.createdAt
    oldestId = id
  }
}
```

5000 次迭代的 O(n) 扫描，虽然不是高频操作但仍可优化。

3. **只淘汰本地不通知 OpenCode**：淘汰后的会话在本地删除，但 OpenCode 进程中仍然存在，浪费 OpenCode 进程的资源。

## 改进方向

1. 使用小顶堆（MinHeap）按创建时间排序，O(log n) 淘汰
2. 或维护一个排序的会话 ID 列表
3. 淘汰时同步删除 OpenCode 中的会话（`client.session.delete()`）
